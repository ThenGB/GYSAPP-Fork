# GYSAPP-Fork Codebase Audit — 2026-08-09

## Executive summary

The application is not a uniformly inefficient codebase. Several performance-sensitive areas have already been deliberately optimized: Bible split-scroll throttling, MIDI targeted rebuilds, lazy Bible database initialization, PDF streaming, asset-manifest access, song search caching, and background initial-state work.

The highest-value issues found in this audit were concentrated in application bootstrap, debug instrumentation, persistence I/O, theme parity, and duplicated UI composition. Those areas are addressed in this branch without rewriting working Bible/PDF/MIDI architecture.

This audit cannot prove the absence of every bug. The quality target is instead: remove known defects, add regression coverage, make failure modes visible, and establish CI so future regressions are caught automatically.

## Fixed in this branch

### 1. Marionette runtime removed

**Severity: high / unwanted runtime instrumentation**

`marionette_flutter` was a direct application dependency and `MarionetteBinding.ensureInitialized()` was called from both `main.dart` and `app.dart` in debug native builds.

Changes:
- removed the package from `pubspec.yaml`;
- removed all Marionette imports and binding initialization;
- standardized startup on `WidgetsFlutterBinding`;
- added a regression test that rejects Marionette references in app bootstrap and pubspec.

`pubspec.lock` is regenerated by `flutter pub get` in CI. The committed lockfile should be refreshed from a Flutter-enabled development environment after dependency resolution is confirmed.

### 2. Translation refresh no longer performs redundant network preflight

**Severity: medium / latency + unnecessary network work**

The translation refresh previously performed:
1. connectivity plugin check;
2. DNS lookup against Google;
3. actual translation HTTP request.

Only step 3 is needed because the HTTP request already has timeout/error handling and is the authoritative reachability check.

Changes:
- removed the connectivity/DNS preflight;
- removed the now-unused `connectivity_plus` direct dependency;
- kept translation refresh fire-and-forget so it never delays the first usable frame;
- limited translation logging to debug builds.

### 3. Required dependency injection no longer fails silently

**Severity: high / correctness**

Previously `setupInjection()` could time out/fail and `initApplication()` would continue. The first feature to request a missing registration would then fail later with a misleading runtime exception.

Now required DI setup is allowed to fail at the bootstrap boundary where the actual root cause is visible. Optional notification/PDF initialization remains non-blocking and guarded.

### 4. Song/MIDI graph deferred until first use

**Severity: medium / cold-start performance**

`SongCubit` was registered as an eager singleton, constructing its dependency graph during `setupInjection()` before `runApp()`.

It is now a lazy singleton, matching the already-correct BibleCubit strategy. App-level `BlocProvider` remains lazy by default, so the song engine is created only when a widget first requests it.

### 5. Desktop path-provider calls run concurrently

**Severity: low-medium / desktop cold-start latency**

Application documents, temporary, and support directories are independent calls. They are now resolved through `Future.wait` instead of serially.

### 6. Hydrated state persistence avoids forced fsync per mutation

**Severity: medium / interaction and I/O performance**

Native HydratedBloc storage previously logged every cache read/write and used `flush: true` for every state write.

Changes:
- release builds no longer emit per-state developer logs;
- file writes use normal OS buffering instead of forcing a physical flush for each mutation;
- the in-memory cache remains the synchronous read path required by HydratedBloc.

### 7. Migration marker corrected

**Severity: medium / data migration correctness**

The app package version was `2.1.0`, but the Android storage migration marker used `2.0.30`. The migration is explicitly a pre-2.1 migration, so its marker now records `2.1.0` and the wipe only applies to versions older than 2.1.

## UI / UX modernization

### Hymn selector

The song selector has been redesigned around two explicit browse modes:
- **Daftar** — dense, fast scanning with number badge, title, lyric preview and playlist action;
- **Kotak** — responsive visual cards with number, title, lyric preview and book context.

Both modes use lazy builders and retain:
- debounced/memoized search;
- number/title/first-lyric matching;
- song-book switching;
- last-opened/resume action;
- playlist create/add/remove/activate/open flows;
- keyboard dismissal on scroll;
- `RepaintBoundary` around repeated song cells.

### Theme parity

Light and dark themes previously used materially different type scales and component radii. Dark mode now uses the same hierarchy and control geometry as light mode, while retaining its own color scheme.

This prevents theme switching from changing layout density and emphasis.

## Existing optimizations reviewed and intentionally retained

The following patterns should **not** be removed by generic cleanup passes:

- `InitialCubit` marks the UI loaded first and runs internet/PDF/config/theme preparation in the background.
- `BibleCubit` is a lazy singleton because desktop SQLite FFI isolate startup is unsafe during early DI bootstrap.
- Bible split-scroll visibility updates are throttled rather than firing every frame.
- MIDI position ticks are isolated with `ValueNotifier`/stream handling instead of rebuilding the entire player.
- MIDI drag/snap animation isolates high-frequency position changes.
- Song PDF rendering uses native `pdfrx` paths rather than base64/WebView handoff.
- Local asset discovery uses Flutter's asset manifest API.
- Song list filtering is memoized and user input is debounced.
- Existing source-hygiene tests protect several of these decisions.

## Remaining audit findings / follow-up candidates

### A. `use_build_context_synchronously` is suppressed in multiple feature files

**Risk: medium**

Occurrences remain in Bible, Song, Faith and selected-verse flows. Suppression does not automatically mean a bug, but each asynchronous navigation/dialog sequence should eventually be converted to explicit `mounted`/context-liveness checks rather than file-wide ignores.

Recommended follow-up: migrate one feature at a time with widget tests; do not mass-edit these paths.

### B. Android package-private paths are still hardcoded in a few storage paths

**Risk: medium / portability**

The DI directory and HydratedBloc storage intentionally use `/data/data/id.sch.kanaan.egys` on Android. This is fast and currently matches the package, but it couples storage code to the application ID.

Recommended follow-up: inject `AppDirectory` into every native storage implementation so the package path has one source of truth.

### C. Several major screens still hand-compose AppBars and cards

**Risk: UI consistency, low runtime risk**

The repository already contains a `DesignSystem` and unified components, but Bible, Song, Home and some settings screens still override header geometry locally.

This branch fixes theme-token parity and the hymn selector first. A safe next UI pass should migrate screens to a shared page-header/surface primitive incrementally, with screenshot/device review after each feature. Replacing every header in one blind patch would create more regression risk than value.

### D. Dependency surface is broad

**Risk: build size / maintenance**

The app has a large but feature-driven dependency set (PDF, audio, MIDI, SQLite across platforms, auth, editor, notifications, webview). No dependency should be removed solely because it looks large.

The direct dependencies removed in this audit were proven unused after source changes (`marionette_flutter`, `connectivity_plus`). Further pruning should be based on source-reference checks plus builds for Android, Windows and web.

### E. Persistence durability trade-off

Hydrated state writes no longer force `flush: true` on every mutation. This is appropriate for reconstructible UI state and removes synchronous storage pressure. Critical downloaded assets/configuration continue to use their own storage services and were not changed by this optimization.

## Quality strategy added

A GitHub Actions workflow now runs on `main`, `agent/**` and pull requests:

1. install stable Flutter;
2. `flutter pub get`;
3. `flutter analyze`;
4. `flutter test`.

A modernization hygiene test verifies:
- Marionette is absent;
- translation loading has no connectivity/DNS preflight;
- hymn selector exposes list and grid implementations;
- dark/light primary typography scale stays aligned.

## Manual validation checklist

Before merge, test on at least one narrow phone and one desktop/tablet-sized viewport:

- cold launch to Dashboard;
- dark/light switch;
- open Pujian selector;
- switch Daftar ↔ Kotak repeatedly;
- search by song number, title and lyric word;
- change hymn book while search is active;
- open a song from each view mode;
- create a playlist and add/remove songs;
- activate playlist and verify MIDI auto-next behavior remains correct;
- Bible open/read/split mode smoke test;
- PDF hymn open/fit/two-page smoke test;
- MIDI play/pause/drag/expand smoke test;
- settings/theme preferences persistence across restart.

## Definition of “clean” for this repository

For a cross-platform Flutter application this size, “bug-free” cannot responsibly be guaranteed by inspection. A maintainable definition is:

- analyzer has no new errors;
- automated tests pass;
- source-hygiene invariants pass;
- no unwanted debug/runtime instrumentation ships;
- high-frequency paths avoid broad rebuild/log/I/O work;
- optional startup services cannot block first navigation;
- visual tokens are shared between light/dark modes;
- feature-specific refactors include regression tests.
